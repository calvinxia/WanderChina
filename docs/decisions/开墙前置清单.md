## 一、先认清现状:flag 机制的实际能力

数据库 `feature_flags` 表里有 6 项,但**并非全部都被代码读取**。开墙前必须知道哪些真能用:

| Flag | 实现状态 | 实际作用 |
|---|---|---|
| `paywall_enabled` | ✅ 已实现 | 总开关。false 时 `check_user_quota` 直接返回 allowed |
| `paywall_trigger_itinerary_count` | ✅ 已实现 | 行程生成免费次数(默认 3),基于 `users.trips_count` |
| `paywall_trigger_voice_daily` | ✅ 已实现 | 语音翻译每日上限(默认 5),基于 `usage_quota` 表 |
| `paywall_trigger_ai_edit` | ✅ 已实现 | 布尔。true = AI 编辑仅付费用户可用 |
| **`paywall_gates`** | ❌ **未实现** | **代码从不读取。见下** |
| `pricing_override` | ❓ 待确认 | 未在已阅代码中出现,需确认是否有任何调用 |

### ⚠️ `paywall_gates` 不存在

`check_user_quota/index.py` 与 `shared/quota_check.py` 均未读取该 flag。真正起门禁作用的是 `index.py` 里的**硬编码白名单**:

```python
if quota_type not in ('itinerary', 'voice_translate', 'ai_edit'):
```

**含义:**
- **没有"按功能粒度开墙"的能力** —— 无法只对行程生成收费、语音保持免费
- 开墙时三个功能一起进入配额限制
- 唯一的间接手段:把某功能的 `paywall_trigger_*` 阈值调到极大(如语音日限设 999),等效于该功能不限

**两条路,开墙前二选一:**
- **(a) 补实现** —— 在 `index.py` 的总开关判断后加一层:读 `paywall_gates`,若不含当前 `quota_type` 则直接放行。改动小,换来按功能开墙的灵活度
- **(b) 删除该 flag** —— 承认它不存在,避免将来误以为在生效

> 建议 (a)。开墙初期很可能想"只对最贵的功能(行程生成)收费,语音先免费养用量",届时这个能力有实际价值。

### A2 · ✅ 已修复 · 数据库连接泄漏
`check_user_quota/index.py` 中:
```python
conn = get_db_connection()
cursor = conn.cursor()
conn = get_db_connection()   # ← 重复,第一个 conn 被覆盖后永不释放
cursor = conn.cursor()       # ← 重复
```
- 全函数只 `cursor.close()`,`conn` 从未关闭
- SCF 容器复用会累积,最终吃满数据库连接数
- [x] 删除重复两行
- [ ] ⚠️ **待确认**:`get_db_connection()` 是否全局复用连接;若非,需在 `finally` 中关闭 conn(仅删重复行不足以杜绝泄漏)

### A3 · 🟡 跨日重置的时区来源不一致
同一个"今天"用了两套时区:
```python
# check(容器时区)
if last_reset_at.date() < date.today():

# increment(数据库时区)
WHEN usage_quota.last_reset_at::date < CURRENT_DATE
```
- SCF 容器与 PostgreSQL 时区若不同(容器 UTC / 库东八区),在两者跨日的时间窗内:check 判定已重置放行,increment 却按未跨日 +1 —— 用户看到的额度与实际扣减不符
- [ ] 统一时区来源:让 check 也走数据库判断(如查询时顺带取 `CURRENT_DATE`,或在 SQL 内直接算 `used_today`)

### A4 · ✅ 已修复 · 后端与客户端的默认值方向相反
```python
paywall_enabled = master_flag.get('paywall_enabled', True)  # 后端缺失默认 True
```
- 客户端(本次改动)约定 **fail-closed = false**(不误扣款)
- 后端默认 **True**(保护收入)
- **坏情况:** flag 读取异常时,后端开始拦功能、客户端隐藏升级入口 → **用户被拦住却看不到任何付费入口**
- [x] 已统一方向 —— 后端改为缺失时默认 `False`,与客户端 fail-closed 一致
- [ ] ⚠️ **待确认**:确认改的是 `False` 而非两端都 `True`(方向反了会重新制造死胡同)

### A5 · ✅ 已修复 · 购买取消时抛 TypeError

- [x] iOS 侧 `AppStorePurchaseDetails` 强转同步检查

## 三、阻塞项 B · 逻辑漏洞(开墙前必查)

### B1 · 🔴 **已确认的活漏洞** · 删除行程可重置免费额度

**核查结论(2026-08-09,经两次修正后的最终事实):**
- 前端有删除入口(`planner_home_screen.dart:464` 有 `Failed to delete trip` 错误处理)
- **后端已实现** —— 不在独立的 `delete_trip` 函数中,而在 **`create_trip/index.py` 的 `action == 'delete'` 分支**
- 该分支**确实递减计数**:

```python
UPDATE users SET trips_count = GREATEST(trips_count - 1, 0)
WHERE id = %s
```

**完整利用链:**
```
建 3 个行程 → trips_count = 3 → 达免费上限被拦
删除 3 个行程 → trips_count = 0
再建 3 个 → 免费额度重置,循环无限
```

`GREATEST(…, 0)` 只防负数,防不住此循环。

> **当前无实际损失**(`paywall_enabled = false`,配额判断不生效),但**开墙当天即成为可被立刻利用的漏洞**,且这类玩法在用户间传播极快。

**修复方案(建议在开墙前完成语义分离):**

- [ ] 🔴 **新增只增不减的累计字段**,如 `users.trips_created_total`
      - `create` 分支:`trips_created_total + 1`(与现有 `trips_count + 1` 并行)
      - `delete` 分支:**只减 `trips_count`,不动 `trips_created_total`**
- [ ] 🔴 **`check_itinerary_quota` 改用 `trips_created_total` 判断配额**
- [ ] `trips_count` 保留原语义,仅用于展示"当前拥有几个行程"
- [ ] 存量数据迁移:`UPDATE users SET trips_created_total = trips_count`(近似值;已删除的历史无法追溯,可接受)

> **为什么必须分离而非"删除时不减计数":** 若 delete 不减 `trips_count`,用户删光行程后 profile 仍显示"我有 5 个行程",展示语义就错了。两个字段各司其职才是正解。

**顺带记录(与本项无关的观察):**
- delete 的事务处理**正确** —— `trip_days` 先删,若 trips 的 ownership 校验未通过则 `conn.rollback()`,不会误删他人数据
- `action == 'get'` 无 ownership 校验 —— 任何人持 trip_id 即可读取任意行程。trip_id 是 UUID(不可猜),风险低;且将来分享功能上线时行程页本就要公开访问,可能属既定设计。**记录备查,不作为开墙阻塞项**

## 五、开墙执行顺序

```
[前置] 商业条件 C 全部就位(公司 / 收款 / 税务 / 定价)
   ↓
[1] 修完技术缺陷 A1–A6、查完逻辑漏洞 B1–B2,发一个版本
   ↓
[2] 沙盒全流程验证(见第六节)—— flag 仍为 false
   ↓
[3] 设定阈值:paywall_trigger_* 三项
   ↓
[4] (若已补实现)设定 paywall_gates,决定首轮开墙功能
   ↓
[5] 翻 paywall_enabled = true
   ↓
[6] 等待生效:Redis TTL 5 分钟 + 客户端下次启动/进入 profile
   ↓
[7] 密切监控(见第七节)
```

**⚠️ 生效延迟提醒:**
- Redis 缓存 TTL 5 分钟 —— 数据库改完后端最多 5 分钟感知
- 客户端 `FeatureFlagsService` 仅在启动与进入 profile 时拉取 —— 正开着 app 的用户需重启或走进 profile 才看到升级入口
- **fail-closed 的代价:** 开墙当天网络不佳的用户看不到升级入口。方向正确,但需知晓
